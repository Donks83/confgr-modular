# Turning a supplier model into a component

Everything the engine has met so far was generated by `tests/make-test-glb.mjs`,
which only ever produced correct files. A real supplier model is a different
animal, and this is the route from one to the other.

The short version:

```
supplier file  ->  convert to glTF  ->  fix units, origin, names  ->  add snap
planes  ->  declare  ->  inspect  ->  component
```

Two commands do the mechanical parts:

```bash
node tools/inspect-model.mjs <model.glb>     # what is this, and what is wrong with it
node tools/declare.mjs <model.glb> --measure # write the declaration from the geometry
```

`inspect-model` modifies nothing, ever. Run it first, run it again after every
change, and run it last.

---

## 1. Get it into glTF

A supplier will send STEP, IGES, SolidWorks, FBX, 3ds Max or SketchUp. None of
those are runtime formats. Blender imports most of them and exports glTF 2.0.

Convert **before** doing anything else, because conversion usually resets units
and renames nodes — any work done first gets thrown away.

Export as **`.glb`**, not `.gltf`. A `.gltf` needs its sibling `.bin` and image
files, and it only loads where all of them were copied.

`inspect-model` names the format and says so rather than failing obscurely:

```
part.step  1.2 MB  STEP (CAD)
  STEP (CAD) is not a runtime format. Convert to glTF/GLB first...
```

## 2. Units

glTF's unit is the **metre**, and this pipeline authors in metres with the real
size declared separately in millimetres. The loader cross-checks the two and
refuses the file if they disagree — that check is the only thing standing
between us and a scale factor that looks fine on screen and is wrong in AR.

CAD exports are usually in millimetres, so a 600mm cabinet arrives 600 units
wide and renders the size of a building. `inspect-model` tells you what the file
would measure under each reading:

```
Read as        would be (mm)              plausible?
metres         600000 x 720000 x 560000   no
centimetres    6000 x 7200 x 5600         no
millimetres    600 x 720 x 560            yes  <- likeliest
```

Scale the geometry in Blender so it measures in metres, and **apply** the scale
(Object > Apply > Scale). A scale left on the object exports as a node-level
scale, which the inspector reports as `BAKED_SCALE` — it is the usual reason a
model measures right on screen and wrong in the pipeline, and it also skews the
snap planes.

If the declared size and the geometry disagree, the inspector names the factor
rather than describing how to spot one:

```
The geometry is 1000x the declared size. That factor is metres declared as
millimetres — fix the declaration if the model is right, or rescale the model if
the declaration came from the supplier's datasheet.
```

A **different factor per axis** is a stretched model, not a unit error. Find the
non-uniform scale.

## 3. Origin at base centre, Y up

The lowest point of the geometry sits at `y = 0`, and the model is centred on
the origin in X and Z.

Not a style preference:

- AR drops a model onto a detected floor plane. An origin at the mesh centre
  buries half the product in the carpet.
- Rotation happens about the origin. Off-centre, a part swings off its own snap
  points when turned.

## 4. One node called `body`

The visible geometry must be a single node named exactly `body`. The pipeline
refuses to guess which of `Mesh_001`, `Part42` and `Cube.003` is the product.

Join the visible meshes (Blender: select, `Ctrl+J`) and rename. Keep the
snap planes, collision box and dimension box out of it — they are separate nodes
with their own names.

Optional nodes, and what they are for:

| Node | Purpose |
|---|---|
| `col-<part>` | Collision box. A box matching the part's true extent, for when parts have to refuse to overlap. |
| `dim` | Dimension box, for dimension lines and the tear sheet. |

## 5. Snap planes — the part no converter does for you

A snap is a **flat, 4-vertex plane** whose local **+Z** points outward from the
face it sits on. Two snaps may join only if their facings oppose. That is
Mimeeq's red-to-blue rule with the colour metaphor removed.

The name carries the mask:

```
md-snap.<mask>.<label>
```

- **mask** — the kind of joint. Two snaps can only meet if their masks match
  exactly. `carcass-side`, `shelf-level`, `pals`.
- **label** — which one, on this part. `left`, `right`, `level-2-right`.

Exactly two dots. `md-snap.shelf-level` has no label and is refused;
`md-snap.a.b.c` has too many parts and is refused.

In Blender: add a Plane, delete nothing (it is already 4 vertices), rotate so
its normal points out of the face, and position it where the two parts touch.
Snap centres coincide exactly when connected, so the plane goes on the mating
surface, not inset behind it.

Watch out for:

- **Subdivided planes.** A plane with 9 vertices is refused. No subdivisions.
- **Thickness.** Solidify or an extrude makes it not flat, and it is refused.
- **A vertical facing.** Snaps face horizontally. Local +Z pointing up or down
  has no yaw that could align it, and the solver says so.
- **Name collisions.** three.js strips `. : / [ ]` from node names, so
  `md-snap.a.bc` and `md-snap.ab.c` are the same object to it. The loader
  refuses the file rather than attaching a snap to the wrong face. (Dots in a
  correct snap name are fine — the loader reads names from the raw glTF JSON
  precisely so they survive.)

### Roles: which end offers, which end takes

Every snap is a **socket** (offers a place), a **plug** (takes one), or neither.
Two of the same kind never join.

This exists because of a real bug. Every rack snap shared the `shelf-level`
mask, so an upright matched another upright, and the solver does not refuse on
facing — given two snaps pointing the same way it yaws the part 180° to make
them oppose. So it placed an upright straight through a shelf. Roles are the
fix; a facing check would have done nothing.

The rule of thumb: the thing that stays put offers sockets, the thing that
arrives presents plugs. An upright carries sockets at every level **on both
faces** — a middle upright in a three-bay run has shelves on both sides, and
without the second face you cannot put an upright on the far end of a shelf. A
shelf carries a plug at **each end**, for the same reason.

Leave the role off for a plain chain of identical parts, where either end can
meet either end.

Roles are **not measured** and `--measure` will never invent one. They are a
decision about how the range assembles, and a wrong guess produces a model that
connects incorrectly and silently.

### Grids, for a field of attach points

Where a part has rows and columns of attach points — MOLLE webbing, a pegboard,
a slotted upright — one grid plane replaces dozens of snaps:

```
md-grid.<mask>.<label>
```

The plane's drawn size must equal `cols x pitchX` by `rows x pitchY`, or the
markers will not sit on the real webbing and nothing about the render will look
wrong. The inspector checks this.

Columns run along the plane's local +X, rows along local +Y, facing is local +Z.
Cell (0,0) is the min corner — bottom-left looking at the panel.

## 6. Declare it

Blender cannot write scene extras. Its glTF exporter maps object custom
properties to *node* extras, and there is no route to *scene* extras at all,
which is where this pipeline reads from.

So the declaration is a separate step, and a separate file:

```bash
node tools/declare.mjs YOUK-upright-1800.glb --measure
```

That measures the geometry, writes the size into the GLB, and saves a sidecar:

```json
{
  "confgr": { "widthMm": 60, "heightMm": 1800, "depthMm": 400, "unitScale": "metres" },
  "confgrRoles": {
    "md-snap.shelf-level.level-1-right": null,
    "md-snap.shelf-level.level-1-left": null
  }
}
```

Every snap is listed with a `null` role, so the file itself is the checklist of
decisions still to make. Fill them in, then apply:

```bash
node tools/declare.mjs YOUK-upright-1800.glb
```

Two things worth knowing:

- **The sidecar is the reviewable artefact.** A change from 600mm to 900mm is a
  one-line diff in git, not a difference between two binary files. Commit it
  next to the model.
- **Re-exporting geometry does not lose the declaration.** Overwrite the GLB
  from Blender and run `--measure` again: the size is re-measured and the roles,
  grid definitions, spans and options are carried over. It says how many it kept.

`declare.mjs` refuses a declaration that could not load — a role that is not
`socket` or `plug`, a grid missing its pitch, a snap name the model does not
have — and writes nothing when it refuses. Extras it does not own (a supplier's
own part numbers, say) are left alone.

The full set of keys:

| Key | What it holds |
|---|---|
| `confgr` | `{ widthMm, heightMm, depthMm, unitScale }` — the real size. Required. |
| `confgrRoles` | `{ "<snap node>": "socket" \| "plug" }` |
| `confgrGrids` | `{ "<grid node>": { cols, rows, pitchXMm, pitchYMm } }` |
| `confgrSpans` | `{ "<snap node>": { cols, rows } }` — for a part covering several grid cells |
| `confgrOptions` | Per-part options: finishes, materials |

## 7. Inspect until it is clean

```bash
node tools/inspect-model.mjs models/           # a whole folder
node tools/inspect-model.mjs model.glb --json  # machine-readable
```

**Blockers** are what the loader actually throws on, with the same error codes,
listed in the order they have to be fixed — no point centring an origin on a
model whose units are wrong. The loader stops at the first one; a real file has
several, so all of them are reported at once.

**Warnings** load fine and bite later. Most of them have bitten already.

Exit code is 0 when every file inspected has no blockers, so this drops into CI
as-is.

## 8. AR-safe by default

The nine rules from `confgr-modular-plan.md` §7.6 exist so that adding "view in
your room" later is a feature, not a rebuild. Most are enforced above; the rest
are worth knowing now:

1. **Real-world scale, declared and cross-checked.** §2, §6.
2. **Origin at base centre, Y up.** §3.
3. **One named `body` node.** §4.
4. **Static mesh.** No animation, no skinning — neither survives the USDZ
   conversion iOS needs. Reported as `NOT_STATIC`.
5. **Triangulated.** Strips and fans render but convert badly. Reported as
   `NON_TRIANGLE_PRIMITIVES`.
6. **PBR metallic-roughness materials.** The one material model that travels.
7. **Explicit option defaults.** So a saved configuration always resolves to the
   same appearance.
8. **Self-contained.** `.glb`, with textures embedded. Reported as
   `EXTERNAL_TEXTURES`.
9. **A triangle budget.** Fine for one hero part is too heavy for twenty in a
   configuration, and a phone running AR is the real constraint. Reported over
   150k triangles per component.

## Worked example

```bash
# 1. Convert in Blender, export as GLB. Then:
node tools/inspect-model.mjs YOUK-upright-1800.glb

#    -> NO_DECLARED_SIZE, NO_BODY, NO_SNAPS, and millimetres as the likeliest unit

# 2. In Blender: scale to metres and apply, move base to y=0, centre in plan,
#    join and rename to "body", add the snap planes.
node tools/inspect-model.mjs YOUK-upright-1800.glb

#    -> NO_DECLARED_SIZE only

# 3. Declare, fill in the roles, apply.
node tools/declare.mjs YOUK-upright-1800.glb --measure
$EDITOR YOUK-upright-1800.confgr.json
node tools/declare.mjs YOUK-upright-1800.glb

#    -> loads as a component

# 4. Drop it in test-assets/ and open the app.
```

## Reference implementation

`tests/make-test-glb.mjs` builds correct components from scratch with no
dependencies, and is the reference for every convention above. When a rule here
and that file disagree, that file is right and this one needs fixing.
